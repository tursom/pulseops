# PulseOps 前端优化功能需求对齐稿

## 1. 背景

PulseOps 当前已经具备任务运行态查看、任务配置 CRUD、运行详情、AI 分析、数据处理任务、任务流/依赖画布和全局设置等前端能力。但页面更像“后端接口的直接映射”，没有按实际使用场景组织信息：

- 首页只有任务数量统计，不能快速回答“现在最需要处理什么”。
- 任务运维、任务配置、依赖编排混在同一层级，值班人员和配置人员的入口不清晰。
- 任务详情和运行详情偏原始字段展示，失败定位路径长。
- 任务创建表单直接暴露底层配置、JSON、JQ、模板变量，缺少默认向导和验证反馈。
- “流水线”不是既定业务术语，当前实际承担任务分组和依赖拓扑职责，应调整为更准确的“依赖拓扑”。

本文件先固定功能需求和信息架构，作为后续 UI 设计和前端实现的依据。

## 2. 目标

### 2.0 工程约束

PulseOps 是开发中的全新服务，当前可以接受任意破坏性变动。后续前后端重构应优先选择清晰、长期可演进的数据模型和 API 契约，不需要为了兼容现有页面、接口、字段、表结构或配置文件格式做折中。

因此，本轮允许：

- 重命名或删除现有 API。
- 调整数据库表结构和字段语义。
- 重构 `TaskDefinition`、依赖关系、运行记录和平台配置模型。
- 改造前端路由、页面结构和组件边界。
- 提供一次性迁移脚本或直接重建开发环境数据。

### 2.1 产品目标

PulseOps 前端应优先成为一个内部运维工作台，而不是配置字段编辑器。核心目标：

1. 让值班人员在进入页面后 30 秒内知道当前异常任务、影响范围和下一步动作。
2. 让研发/平台人员能低成本创建、调整和验证巡检任务。
3. 让任务依赖关系可视化，清楚展示上游输出、下游触发和异常传播。
4. 让 AI 分析结果服务于诊断流程，而不是作为孤立的原始记录。

### 2.2 非目标

- 不在本轮把 PulseOps 做成完整告警编排平台。
- 不在本轮落地完整 DAG 工作流引擎的全部能力；但依赖拓扑、数据模型和 API 设计必须为未来通用 DAG 编排预留扩展空间。
- 不在本轮实现权限、登录和操作审计；访问控制依赖外层 Pangolin 保护。
- 不在前端绕过后端做任务执行、告警或安全校验。
- 不在本轮强制规范标签维度；后续如需要可再约束 `env`、`service`、`domain` 等推荐标签。

## 3. 用户角色

| 角色 | 主要诉求 | 典型操作 |
| --- | --- | --- |
| 值班/运维人员 | 快速发现异常、判断影响、触发重跑或禁用任务 | 看概览、筛失败、进运行详情、重跑、禁用、查看 AI 诊断 |
| 研发/平台配置者 | 创建和维护任务，调试数据源、表达式、依赖触发 | 新建任务、编辑参数、测试配置、设置上游/下游、查看样本数据 |
| 平台管理员 | 维护全局留痕、Sink、AI、对象存储和启动配置等平台能力 | 修改全局设置、确认存储策略、查看配置风险、人工恢复错误配置 |

## 4. 信息架构

建议将导航从“接口模块”调整为“工作场景”：

| 一级入口 | 定位 | 替代/覆盖现有页面 |
| --- | --- | --- |
| 工作台 | 异常优先的运行总览 | `Dashboard` |
| 任务监控 | 所有任务的运行态列表和批量操作 | `TaskList` |
| 任务配置 | 创建、编辑、模板、验证任务定义 | `TaskEditor` / `TaskForm` |
| 依赖拓扑 | 任务组、依赖关系、上下游影响面 | `PipelineList` / `PipelineEditor` |
| 运行记录 | 跨任务的执行历史检索，P1 可先不单独成页 | `TaskDetail` 内运行历史 |
| 平台设置 | 全局追踪、Sink、AI、对象存储配置 | `Settings` |

说明：

- “流水线”不是既定术语，统一改为“依赖拓扑”。如后续需要表达分组概念，可使用“任务组”作为辅助概念。
- 任务配置可作为任务监控和依赖拓扑里的动作入口，不一定必须长期作为一级导航。
- PulseOps 当前主要面向内部值班和研发用户，不需要面向非研发运营人员做低代码包装。

## 5. 核心流程

### 5.1 异常处理流程

1. 用户进入工作台。
2. 页面优先展示异常队列：失败任务、检查未通过、加载失败、长时间未运行、耗时异常。
3. 用户点击异常任务进入任务详情。
4. 任务详情展示最近一次失败摘要、上游/下游影响、最近运行趋势和推荐动作。
5. 用户进入运行详情查看错误、摘要、Payload、Findings、产物和 AI 诊断。
6. 用户可重跑任务、禁用任务、编辑配置，或跳转到依赖拓扑查看影响面。

### 5.2 创建任务流程

1. 用户选择任务模板：HTTP、TCP、脚本、进程、场景巡检、数据处理、AI 分析。
2. 向导分步填写：基本信息、调度/触发、任务参数、留痕/告警、预览与验证。
3. 参数页按任务类型展示业务化字段，复杂字段进入高级模式。
4. 保存前完成前端校验；如后端支持，调用验证/试运行接口。
5. 创建成功后跳转到任务详情或所属依赖拓扑。

### 5.3 数据处理/AI 联动流程

1. 用户在上游任务详情或拓扑节点上创建下游数据处理/AI 分析任务。
2. 表单自动带入上游任务。
3. 页面展示上游最近一次成功运行的 `summary`、`record`、`payload` 样本。
4. 用户通过字段选择器或高级 JQ 模式定义提取字段。
5. AI 分析任务可以复用上游输出、运行历史、历史分析等数据源。
6. 下游任务执行后，任务详情展示提取字段、样本值、AI 输出和 Findings。

### 5.4 依赖调整流程

1. 用户进入依赖拓扑，查看任务组整体健康状态。
2. 用户拖拽连线创建依赖，选择触发条件。
3. 用户点击边编辑触发条件或删除依赖。
4. 用户右键/菜单从节点创建下游任务。
5. 保存后拓扑和任务定义保持一致。

目标形态需要支持一个任务监听多个上游。每个上游应作为一个独立数据源配置，同时允许多个上游复用公共参数，例如授权信息、Header 模板、超时策略等。当前后端 `TaskDefinition` 仅支持单个 `watch_task_id`，需要扩展依赖模型和触发语义。

## 6. 页面功能需求

### 6.1 工作台

工作台应从“统计卡片”升级为“异常优先”的首页。

必须包含：

- 全局健康状态：正常、存在失败、存在配置加载错误、数据加载失败。
- 自动刷新状态：最近刷新时间、刷新间隔、手动刷新。
- 核心指标：任务总数、启用任务、失败任务、检查未通过任务、加载失败任务。
- 异常队列：按优先级展示失败、超时、检查失败、`last_reload_error`、长时间未运行。
- 最近运行：展示最近 N 次任务执行结果，支持跳转运行详情。
- 标签聚合：按 `env`、`service`、`kind` 展示异常分布。
- 快捷入口：创建任务、查看全部失败任务、进入依赖拓扑。

P1 可增加：

- 耗时异常检测，例如本次耗时明显高于最近均值。
- 最近 AI 诊断摘要。
- 任务组/依赖拓扑健康概览。

### 6.2 任务监控列表

任务列表应服务运维排查，而不是只展示配置字段。

必须包含：

- 搜索：任务名称、任务 ID、错误信息。
- 筛选：任务类型、启用状态、运行状态、检查状态、运行时状态、标签 `env/service/domain`。
- 排序：异常优先、上次运行时间、下次运行时间、耗时、更新时间。
- 列字段：任务名/ID、类型、标签、启用、运行态、上次运行、上次结果、检查结果、耗时、下次运行、错误摘要、操作。
- 行操作：立即执行、启用/禁用、编辑、查看详情。
- 批量操作：批量执行、启用、禁用；执行后展示成功/失败明细。
- URL 参数与筛选状态同步，工作台跳转到失败列表时筛选应生效。

P1 可增加：

- 服务端分页、服务端筛选。
- 保存常用筛选视图。
- 任务变更审计入口。

### 6.3 任务详情

任务详情应先回答“这个任务现在是否健康，为什么，下一步做什么”。

必须包含：

- 顶部摘要：任务名称、类型、启用状态、运行态、上次检查结果、上次运行结果。
- 操作区：立即执行、启用/禁用、编辑、刷新、进入拓扑。
- 健康摘要：最近失败原因、最近成功时间、下次运行时间、连续失败次数（如后端可提供）。
- 依赖信息：上游任务、下游任务、触发条件、所属任务组。
- 趋势：耗时趋势、成功/失败分布。
- 运行历史：分页、筛选时间范围、点击进入运行详情。
- 配置摘要：调度、触发、关键参数、留痕、告警。
- AI 分析：最近分析结果摘要，异常任务优先展示。

数据处理任务额外要求：

- 展示源任务和源任务最近运行状态。
- 展示提取表达式、样本值、聚合方式。
- 支持跳转到源任务样本和运行详情。

### 6.4 运行详情

运行详情应作为单次执行的诊断页面。

必须包含：

- 概述：运行 ID、任务 ID、触发方式、运行状态、检查状态、开始/结束时间、耗时、错误信息。
- 诊断优先区：错误、检查发现、AI 结论摘要。
- 结构化摘要：`summary` 以可读 JSON/表格方式展示。
- 原始数据：`payload`、`stdout`、`stderr`，支持复制、搜索、展开、下载。
- Findings：级别、规则 ID、消息、详情。
- Artifacts：类型、大小、预览、下载。
- AI 分析：提示词、回复、token、耗时、错误；默认展示结论，原文折叠。
- 操作：重跑、返回任务、打开任务配置。

P1 可增加：

- JSON 路径复制。
- 大文本虚拟滚动。
- 对比两次运行差异。

### 6.5 任务配置

任务配置应保留高级能力，但默认走向导。

必须包含：

- 模板入口：HTTP 检查、TCP 检查、脚本执行、进程检查、场景巡检、数据处理、AI 分析。
- 分步表单：基本信息、调度/触发、参数、留痕/告警、预览确认。
- 调度校验：`interval` 与 `cron` 互斥；`manual` 任务不强制调度。
- 参数校验：
  - HTTP：URL、方法、状态码数组、Header、Body。
  - TCP：`host:port`。
  - 脚本：命令、参数、工作目录、环境变量。
  - 进程：进程名。
  - 场景巡检：源接口、采样、fanout、evaluator、阈值。
  - 数据处理：源任务、数据源、字段选择/JQ、聚合。
  - AI 分析：分析类型、数据源、Prompt 模板、输出配置。
- 高级模式：允许查看/编辑原始 JSON 或 TOML 形态，但需要明确风险提示。
- 保存反馈：创建/更新成功后明确跳转目标。

P1 需要后端配合：

- 任务定义验证接口。
- 试运行/干跑接口。
- 表达式校验接口。

### 6.6 依赖拓扑

依赖拓扑应同时支持“看状态”和“改依赖”。

必须包含：

- 任务组列表：名称、描述、任务数、异常数、最近更新时间。
- 拓扑画布：节点、边、触发条件、节点状态、最近运行结果。
- 画布操作：缩放、平移、自动布局、刷新、导入任务、创建任务。
- 节点操作：查看详情、编辑、执行、启用/禁用、创建下游、删除。
- 边操作：查看/编辑触发条件、删除依赖。
- 侧边详情：选中节点/边后展示详情，避免所有操作都依赖右键。
- 空状态：引导创建任务或导入任务。

P1 可增加：

- Minimap、按状态/类型/标签筛选节点。
- 异常影响路径高亮。
- 多任务组之间移动任务。

### 6.7 平台设置

平台设置应从“少量字段表单”扩展为配置管理中心。除极少数必须由部署系统提供的启动参数外，平台运行配置应逐步迁移到前端可管理的 DB 配置中。

必须包含：

- 追踪默认值：最大内联 Payload、默认保留天数。
- Sink 管理：Postgres、Webhook；至少保留一个 Postgres Sink。
- AI 配置：开关、Provider、endpoint、模型、超时、max tokens、temperature、插件目录。
- 对象存储配置：provider、bucket、endpoint、region、base path、presign TTL、path style 等。
- 运行配置摘要：当前服务地址、任务配置目录、状态存储、对象存储、AI 开关和模型。
- 配置应用状态：已应用、待重启、应用失败、使用默认兜底。
- 风险提示：删除 Sink、缩短保留期、关闭留痕等操作需要确认。
- 人工恢复能力：配置错误不能让平台无法启动到管理界面；应允许服务以 degraded/config_error 模式启动，并在前端修复配置。

P1 可增加：

- 对象存储连接测试。
- Webhook Sink 测试发送。
- AI Provider 连接测试。

## 7. 交互和视觉原则

- 以运维扫描效率为优先，减少大块装饰卡片，列表和状态密度要足够高。
- 状态色必须稳定：成功绿色、失败红色、超时/降级橙色、禁用灰色、运行中蓝色。
- 主要页面保持中文一致，不混用 `Create Task`、`Edit Task` 等英文标题。
- 操作按钮使用图标 + 明确文本；危险操作必须二次确认。
- 表格、画布、详情页应支持 15 秒自动刷新，但用户编辑时不得自动覆盖表单。
- 空状态要指向下一步动作，而不是只显示“暂无数据”。
- 错误状态要展示可操作信息：重试、查看配置、查看后端错误。
- 默认桌面优先；移动端至少保证可查看工作台、任务列表和运行详情。

## 8. 后端/API 需求缺口

现有 API 已覆盖基本运行态、任务定义、运行记录、AI 分析、产物、任务组和设置。但接口仍以资源 CRUD 和单任务查询为主，前端会被迫自行拼装页面视图。由于 PulseOps 仍是开发中的全新服务，本轮不要求兼容旧接口和旧表结构，建议把后端直接重构为“面向页面和诊断流程”的契约。

| 需求 | 当前状态 | 建议 |
| --- | --- | --- |
| 工作台聚合 | 前端需拉取任务后自行计算 | 新增 `/api/dashboard/summary`，返回异常队列、聚合指标、最近运行 |
| 跨任务运行记录 | 目前主要按任务查询 | 新增 `/api/runs` 支持按状态、时间、标签筛选 |
| 任务列表服务端筛选 | 当前前端内存过滤 | 任务量增长后新增分页、筛选、排序参数 |
| 连续失败次数 | 前端只能看 last 状态 | 后端在 TaskState 或 summary 中提供 |
| 上下游关系 | 当前需从 definitions 推导 | 新增任务依赖查询接口，返回 upstream/downstream |
| 批量操作 | 当前前端循环调用单任务接口 | 新增批量执行/启用/禁用接口并返回逐项结果 |
| 任务定义验证 | 当前保存时才暴露错误 | 新增 validate/test-run/dry-run 接口 |
| 设置覆盖范围 | 当前仅 Sink 和部分 trace 默认值 | 将 AI、Artifact、Trace、运行参数逐步迁移为前端可管理配置，并提供 degraded 启动兜底 |

### 8.1 后端现状判断

当前后端存在几个会直接影响前端重构质量的点：

- `/api/tasks` 只返回 runtime manager 中已加载任务；定义存在但加载失败或未加载的任务需要前端再调 `/api/task-defs` 自行合并。
- `/api/tasks/{id}/runs` 返回完整 `RunRecord`，包含 `payload`、`stdout`、`stderr` 等重字段；列表页实际只需要摘要字段。
- 运行列表查询会逐条补 artifacts，任务历史页容易出现 N+1 查询。
- `/api/settings` 保存后只写 DB，运行中的 trace sink 和 `max_payload_bytes` 没有明确热生效路径；AI、Artifact 等多数配置还依赖启动 TOML。
- 任务依赖只有单个 `watch_task_id`，并且 `watch_condition` 解析较宽松；未知字段或非法表达式会默认匹配，前端无法可靠提示配置错误。
- 任务定义写库与启动不是同一个事务：创建/更新定义成功后，如果启动失败，DB 中会留下无法加载的配置，需要前端有明确的“配置异常”状态。
- 后端缺少任务定义验证、试运行、跨任务运行查询、依赖图查询等面向页面的接口，前端只能拼装。
- 目前启动流程会依赖 PostgreSQL、对象存储等配置成功初始化；如果未来多数配置前端化，需要避免错误配置阻断管理界面启动。

### 8.2 建议优先做的后端协同重构

P0：支持前端重构第一版必须补齐。允许破坏性调整现有 API、表结构和配置模型，优先把核心模型一次性改干净。

| 模块 | 建议接口/改造 | 说明 |
| --- | --- | --- |
| 统一任务视图 | 重设 `GET /api/tasks` 返回 TaskView | 返回 definition + runtime + config_status + load_error，避免前端合并任务定义和运行态；可替换现有响应结构 |
| 工作台摘要 | `GET /api/dashboard/summary?since=24h` | 返回 counts、异常队列、最近运行、按标签聚合，前端首页不再 N 次请求 |
| 轻量运行列表 | 重设 `GET /api/tasks/{id}/runs` 返回 RunListItem | 列表只返回 run_id/status/check/duration/error/summary 摘要，不带 payload/stdout/stderr；详情接口负责完整数据 |
| 运行详情 | 保留 `GET /api/tasks/{id}/runs/{runID}` | 详情页返回统一的 `payload` 字段；后端自动把 inline payload 与 payload artifact 聚合到同一位置 |
| 跨任务运行记录 | `GET /api/runs` | 支持 `task_id/kind/run_status/check_status/since/label/limit/offset` |
| 依赖关系 | `GET /api/task-graph` + 新依赖表 | 返回 nodes/edges，节点含 runtime 摘要，边含 condition 和有效性；不再依赖单个 `watch_task_id` |
| 批量操作 | `POST /api/tasks/batch` | 支持 run/enable/disable/reload，返回逐项成功失败 |
| 任务验证 | `POST /api/task-defs/validate` | 只做解析、Normalize、ValidateBasic、driver Validate，不落库、不启动 |
| 设置热生效 | `PUT /api/settings` 后 reload trace manager | 保存后同步更新 sink 与 max payload bytes，返回 applied 状态 |
| 配置兜底启动 | degraded/config_error 模式 | AI、Artifact、Webhook 等非核心配置错误不应阻断管理界面启动；前端展示错误并允许修复 |
| 多上游依赖模型 | task_dependencies / data_sources | 一个任务可监听多个上游；公共授权、Header、超时等参数可复用；允许废弃现有单上游字段 |

P1：提升稳定性和可维护性。

| 模块 | 建议接口/改造 | 说明 |
| --- | --- | --- |
| 分页与索引 | runs 增加跨任务查询索引 | 至少补 `started_at DESC`、`run_status/check_status`、必要的 labels JSONB 索引 |
| 连续失败统计 | TaskState 增加 `consecutive_failures` | 工作台可以按影响排序，不再前端扫描历史 |
| 下游影响面 | 后端提供 downstream count/list | 删除、禁用、改依赖前展示影响 |
| 配置版本 | task_definitions 增加 version/revision | 支持展示变更历史和回滚 |
| 条件表达式校验 | 严格校验 `watch_condition` | 不支持的字段或格式应保存前报错，不应默认匹配 |
| 配置管理 API | `GET/PUT /api/platform-config` | 管理 AI、Artifact、Trace、HTTP client 等运行配置，标记哪些需重启 |

P2：取决于业务方向。

| 模块 | 建议接口/改造 | 说明 |
| --- | --- | --- |
| 事件推送 | SSE/WebSocket | 替代 10-15 秒轮询，用于工作台和拓扑实时状态 |
| 后端模板库 | task_templates 表或静态注册 | 前端创建向导从后端拉模板和字段 schema |
| DAG 编排能力 | workflow/dag 模型 | 在依赖拓扑基础上演进到通用 DAG，支持并行、汇聚、条件分支、重试策略和执行实例 |
| 权限/审计 | 用户、角色、操作审计 | 当前依赖 Pangolin，不进入近期范围；如后续有合规要求再补 |

## 9. 分阶段落地

### Phase 0：需求对齐与契约重设

- 固定本文档和术语。
- 确认新信息架构、中文标题和导航名称。
- 将“流水线”统一改名为“依赖拓扑”。
- 定稿破坏性 API 调整范围，包括 `TaskView`、轻量运行列表、运行详情、任务验证、设置热生效。
- 定稿破坏性数据模型调整范围，包括任务定义、依赖关系、数据源、运行记录和平台配置。
- 确认配置前端化的启动兜底策略：非核心配置错误不阻断管理界面启动。

### Phase 1：运维工作台重构

- 重做工作台、任务监控列表、任务详情、运行详情的信息层级。
- 后端提供工作台摘要、统一任务视图、跨任务运行查询。
- 保留现有任务编辑能力，只调整入口和基础文案。
- AI 分析结果默认对所有内部用户可见，并纳入异常/预警入口。

### Phase 2：任务配置向导

- 将 TaskForm 改为模板 + 分步表单。
- 为数据处理和 AI 分析补完整的预览、字段选择和高级模式。
- 补充前端校验，并接入后端 validate/test-run/dry-run。
- 支持多上游数据源配置，并支持公共授权、Header、超时等参数复用。

### Phase 3：依赖拓扑增强

- 将任务组列表改为健康概览。
- 画布增加侧边详情、筛选、异常路径高亮。
- 后端提供 task graph 查询，并展示多上游依赖、触发条件和数据源复用关系。
- 依赖模型避免绑定单一 `watch_task_id` 语义，为后续 DAG 节点、边、条件、执行实例和重试策略扩展预留字段与迁移路径。

### Phase 4：平台治理

- 设置页支持 AI、对象存储、Trace、Webhook 等平台配置管理和连接测试。
- 配置错误时平台以 degraded/config_error 模式暴露管理界面，允许人工恢复。
- 权限、审计、团队隔离暂不进入近期范围，访问控制依赖 Pangolin。

## 10. 验收标准

- 用户从工作台进入，能在 2 次点击内打开最近失败任务的运行详情。
- 任务列表可以通过状态、类型、标签快速定位目标任务，工作台跳转筛选生效。
- 任务详情无需展开原始 JSON，即可看到当前健康状态、最近错误、下次运行和上下游关系。
- 运行详情默认展示结论和错误，原始 payload/stdout/stderr 可按需查看。
- 创建一个 HTTP 检查任务无需手写 JSON；创建数据处理任务可基于上游样本选择字段。
- 依赖拓扑既能看节点状态，也能完成多上游依赖创建、编辑和删除。
- AI 分析和 AI 预警默认对所有内部用户可见。
- 平台配置可在前端修改；非核心配置错误不会阻断服务启动到管理界面。
- 所有危险操作有确认，所有异步操作有加载、成功、失败反馈。

## 11. 已确认决策

1. 主要用户为内部值班和研发人员，当前不面向非研发人员。
2. “流水线”不是既定术语，后续统一使用“依赖拓扑”；如需表达分组再使用“任务组”。
3. 暂时不强制标签规范；如后续需要，可再加入推荐或必填标签约束。
4. 暂时不做权限、登录和审计，访问控制依赖 Pangolin。
5. AI 分析和 AI 产生的预警需要默认展示给所有内部用户。
6. 平台应允许从前端管理尽可能多的配置，包括 AI、对象存储、Trace/Sink 等；配置错误应可在前端恢复。
7. 需要支持多上游依赖：一个任务可把多个上游作为独立数据源，并复用公共授权、Header、超时等参数。
